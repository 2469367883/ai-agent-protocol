## 这是什么

这是一份**项目级的 Agent 执行协议**，用来约束 AI agent在本项目中处理代码任务的行为方式。它不是编码规范，而是**"什么时候可以动手、动手到什么程度、出了问题怎么办"**的操作流程定义。

核心诉求只有一句话：**任何涉及代码实现或修改的请求，都必须先经过分析和计划阶段**，未经确认不得直接改代码。

## 解决什么问题

没有这类协议时，AI 编码助手容易走向两个极端：

- **太冲动**：一收到需求就直接改代码，改错了、改多了、改出未经确认的设计决策，用户事后才发现。
- **太啰嗦**：为了保险，每改一行都要停下来问一遍，哪怕是已经明确授权过的计划里的琐碎收尾工作，效率很低。

这份协议试图在两者之间找一条可执行的中线：**首次动手前必须确认，确认之后的执行尽量连贯，不做无意义的重复请示**。

## 协议结构

| 章节 | 解决的问题 |
|---|---|
| 状态定义（讨论态 / 执行态） | 划清"聊需求"和"动代码"的边界，明确哪些只读操作不需要授权 |
| 核心原则（第二章） | 目标模糊时如何暂停、如何提交计划、混合请求怎么处理、如何判定"用户是否已经授权"、原子任务可以连续执行到什么程度 |
| 计划的标准输出格式 | 规定一份"合格的计划"必须包含目标、影响范围、步骤、验证方式，且必须基于已确认的项目现状 |
| 思辨原则（第1章） | 要求 Agent 主动暴露假设、歧义和更简单的方案，而不是揣测后闷头去做 |
| 产出纪律（第2章） | 最小必要修改，贴合项目现有架构，不顺手改无关代码 |
| 代码规范（第3章） | 命名、格式、注释等基础编码要求 |
| Agent 上下文稳定性（第4章） | 防止多轮对话中悄悄丢失约束、重复调用工具、无意义地打散上下文 |
| 执行规范（第5章） | 改动前先核实现状和调用方，改完主动验证一致性 |
| 安全与敏感操作（第6章） | 密钥、鉴权、批量删除等高风险操作强制升级确认 |
| 提交与验证规范（第7章） | 验证失败视为任务未完成，禁止自行判断"问题不大"后继续推进 |

## 关键机制

- **讨论态 / 执行态**：只有"实际改代码 / 执行有副作用的命令"才算执行态；查看文件、grep、git log 等只读操作永远不需要事先授权。
- **智能授权响应**：区分"用户在回答提问" vs "用户在对已提交计划下达指令" vs "用户在提出计划外新要求"，避免要么误判为越权执行，要么陷入反复确认的死循环。
- **原子任务**：获得授权后，单一文件内、职责单一的关联改动可以一次性做完，不必逐步请示；一旦跨文件、涉及配置/依赖/数据/权限，强制回到确认环节。
- **错误熔断**：执行中报错默认立即停止上报；只有修复方式唯一无歧义的语法级错误允许原地修正，但必须在汇报中列出改了什么。

## 如何使用

将本文件放在项目根目录，命名为 `AGENT.md`。协议对该项目内的所有代码类请求生效，与本文件冲突的指令以本文件为准。

**适用场景**：正式项目、多人协作、改动需要留痕和可追溯的场景。协议整体偏保守——哪怕是改一个变量名，首次也需要先出计划再执行。如果项目中有大量一次性、低风险的小改动（如修正 typo、调样式），可以自行评估是否需要为这类任务单独补充豁免规则；协议本身不内置这种豁免。

## 维护建议

修改本协议时注意：

- 各章节之间存在少量有意为之的交叉引用（例如"安全与敏感操作"章重申了"强制暂停点"里已提到的密钥类规则），这是为了强化关键条款，不是冗余，不必合并。
- 若新增条款与已有条款存在字面重叠，先确认是否为"同一件事的两次表达"（应合并，保留信息更完整的一版）还是"不同维度的互补"（应保留），避免像早期版本中"执行态"定义重复且互相矛盾的问题再次出现。
